# view-eval 观测指标（落地后补，暂沉底）

> 日期：2026-09-04
> 状态：**未实现**。`mini_app_view_eval` 已落地并实测通过（commit `f0934db`），本文件承接它「落地后要观察的指标」那一节。
> 相关：`docs/contracts/runtime-diagnostics.md`、`TODO.md` → P2-9

## 为什么单独一篇

P2-9 的设计过程里，几乎每一个被否掉的形态（`mode` 分层、`summary` 独立层、谓语枚举、
selector 地图、`render` 投影参数表）理由都是同一句：**那是在猜 agent 会问什么**。
同样地，「下一步该改哪里」如果继续靠手感，就会退化成同一类猜测——而这次我们手上有信封字段。

所以这不是「加个统计面板」，而是**把下一轮 API 形状决策从猜变成看**。没有这份数据之前
不动 `mini_app_view_eval` 的形态，是唯一的使用约束。

## 要看什么

| 指标 | 决定什么 |
|---|---|
| `code` 长度分布 | 大家都只写一两行 → 注入面三个名字够用；普遍在写长遍历 → 该给「展开到 N 层」那个当时被否掉的旋钮（判据：等证据，不是先做） |
| `bytes` / `maxBytes` 占比 | 长期贴着顶 → 6144 定小了；普遍很低 → 上限合适，别加旋钮 |
| `truncated` + `stoppedBy` 频率（bytes / nodes / depth / timeout 分开） | bytes 多 → 收窄默认投影；nodes 多 → 默认 `treeDepth` 太深或 agent 在 `$$("*")`；depth 多 → 真的有人返回自引用结构 |
| `view` 非 `live` 的比例，按四态分开 | `runner-not-booted` 高 → bundle/runner 可靠性问题（比指标本身更优先）；`not-open` 高 → 工具描述/回路在教人空问；`stuck` 高 → 提示语该更早劝住人别写同步循环 |
| 超时率 + `tookMs` 分布 | 决定 1.2s / 1.5s 两个闸值是否有依据（现在是拍的） |

## 记在哪、别把内存买回来

P2-9 明确删掉了 host 侧的 DOM 常驻缓存（当时的理由：推送式快照的默认采集行为正是我们判定
不该做的事）。所以这里**不能**变成「每个 app 存一份最近视图」，只能存**计数**：

- 每 app 一个定长环形直方图（比如 200 条 `{bytes, maxBytes, ms, stoppedBy, view}`），
  原始 `result` 文本**不落库**——那才是真正会涨内存的东西
- 或者更省：只维护累积计数器和分位数草图（t-digest 级别的手写分桶），不存样本
- 读取面：现有 `HostEventBus` 的 per-app ring 模式已经够用，不要新开 channel 之外的第二套状态

原则一句话：**观测的是分布，不是内容。**

## 触发条件（什么时候值得做）

满足任一即可开工，否则继续放着：

1. 出现第二次「不知道该不该改 `mini_app_view_eval` 形态」的争论——即开始猜了
2. `view` 非 live 比例在真实使用中肉眼可见（>5%），需要归因
3. 有 agent 反复把面板冻成 `stuck`，需要判断是不是提示语没写够

## 明确不做

- 不做 UI / 仪表盘：这是给平台维护者看的一行输出或一个 `GET`，不是产品功能
- 不采 `code` 原文：里面可能有用户数据；分布够了
- 不为了指标引入 headless browser 或任何新运行时依赖（约束 #10）
